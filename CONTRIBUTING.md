# Contributing to MCPFlo

Thanks for your interest in improving MCPFlo. This document covers how to get
set up, the conventions the codebase follows, and how to get a change merged.

## Before you start

For anything beyond a small fix, open an issue first to discuss the change —
it saves you from writing a PR that doesn't fit the project's direction. Bug
reports and feature requests go to the
[issue tracker](https://github.com/harshalslimaye/mcpflo/issues).

## Getting set up

```bash
git clone https://github.com/harshalslimaye/mcpflo.git
cd mcpflo
npm install
npm run dev
```

Requires Node.js 18+ and npm 9+. `npm install` also sets up Husky's
`pre-push` hook, which runs the test suite before every push.

### Project structure

```
src/
├── main/        Electron main process — IPC, MCP client, OAuth, persistence, caching
├── preload/     Typed bridge between main and renderer
├── renderer/    React UI (sidebar, detail views, stores, RJSF forms)
└── shared/      Types shared across processes (MCP schemas, configs)
packages/
└── server-everything/   Test-fixture MCP server used by the e2e suite
```

## Making a change

- Branch off `main`, name the branch `<type>/<short-description>`, e.g.
  `fix/oauth-token-refresh` or `feat/prompt-argument-validation`. Use one of:
  `feat`, `fix`, `docs`, `refactor`, `perf`, `chore`.
- Keep PRs focused — one change per PR is easier to review and revert.
- Every change lands via a pull request into `main`; there's no direct-push
  workflow, even for small fixes.

### Commits

Commit messages should follow
[Conventional Commits](https://www.conventionalcommits.org/), using the same
types as branch names (`feat:`, `fix:`, `docs:`, `refactor:`, `perf:`,
`chore:`). This keeps the changelog (generated by `standard-version`)
accurate — `feat` and `fix` commits show up there; `docs` and `chore` don't.

### Before opening a PR

Run the full local check set:

```bash
npm run typecheck   # type-check main and renderer
npm run lint        # ESLint
npm run format      # Prettier
npm test            # Vitest unit tests
npm run e2e         # Playwright e2e suite (builds first)
```

`npm test` also runs automatically on `git push` via the pre-push hook, so a
push will fail fast if something's broken.

Add or update tests for any behavioral change — unit tests with Vitest for
logic in `src/`, and Playwright e2e coverage in `e2e/` for anything that
touches the running app end-to-end against `@mcpflo/server-everything`.

## Opening the PR

- Describe *why* the change is needed, not just what changed — link the
  issue it addresses if there is one.
- Make sure typecheck, lint, and tests pass locally before requesting review
  (there's no CI pipeline yet, so this is the only check that runs).
- Be responsive to review feedback; small follow-up commits are fine, no
  need to force-push during review.
